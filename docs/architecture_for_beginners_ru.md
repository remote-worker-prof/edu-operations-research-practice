# Архитектура для начинающих

Этот документ объясняет архитектуру проекта простыми словами.
Он не заменяет техническую спецификацию в `docs/architecture.md`, а помогает
сначала понять общую идею, а уже потом углубляться в детали кода и математики.

## TL;DR

Если запомнить только самое главное, то вот оно:

- Это учебное веб-приложение по исследованию операций, а не "магический чат-бот".
- Основной интерфейс теперь открывается на `/app/` и работает как новый React chat shell.
- Пользователь по шагам собирает входы для OR-этапов или extension bundle-а, а затем явно запускает расчёт.
- `apps/webapp` отвечает за HTTP/API и legacy fallback, `apps/chat_web` — за новый чат, `packages/agent_core` ведёт диалог и состояние сессии, `packages/or_core` делает детерминированный расчёт.
- LLM может помочь понять свободный текст и объяснить результат, но не имеет права молча записывать итоговые входы OR-модели.
- Источником истины для расчёта является валидированный `ScenarioDraft`, который превращается в `ORPipelineInput`.
- Любое изменение входов сбрасывает старый `or_result`, чтобы студент не смотрел на устаревший расчёт.
- Проект специально упрощён для обучения: сессии хранятся в памяти, а при недоступном LLM система всё равно продолжает работать.

## 1. Что это за система простыми словами

Проект моделирует следующую учебную историю:

1. Студент общается с ассистентом в чате.
2. Ассистент помогает собрать параметры задачи исследования операций.
3. Когда все входы готовы, студент явно просит запустить расчёт.
4. Система выполняет цепочку из 4 оптимизационных этапов.
5. Студент получает численный результат и объяснение человеческим языком.

Ключевая мысль: здесь есть и диалог, и LLM, но сердце системы не в генерации текста, а в строгом OR-конвейере.

Если сформулировать это строже, то в текущей архитектуре агент поддерживает
не произвольные классы оптимизационных задач, а один фиксированный учебный
OR-конвейер из четырёх этапов: `production -> shipment -> assignment -> routing`.
При этом каждый этап параметризуется входами переменной размерности, заданными
в матрично-векторной форме. Это означает, что пользователь может менять число
объектов внутри поддерживаемой постановки, сохраняя её математический тип и
межэтапные связи. Такой подход соответствует идее учебного агента: система
остаётся объяснимой, детерминированной и методически управляемой, но не сводится
к одному заранее заготовленному примеру.

## 2. Почему проект разделён на `webapp`, `agent_core`, `or_core`

Проект разбит на три слоя, чтобы не смешивать всё в один большой файл и одну большую ответственность.

- `apps/webapp` принимает HTTP-запросы, отдаёт API и держит legacy fallback на `/legacy`.
- `apps/chat_web` даёт основной guided chat shell на `/app/`.
- `packages/agent_core` решает, что делать с очередной репликой пользователя: задать вопрос, применить подтверждённые patch-и, запустить расчёт или объяснить результат.
- `packages/or_core` содержит доменные модели, валидацию и сами OR-решатели.

Если сказать ещё проще:

- `webapp` отвечает на вопрос "как сообщение попало в систему?"
- `agent_core` отвечает на вопрос "что означает это сообщение для диалога?"
- `or_core` отвечает на вопрос "как именно посчитать задачу?"

Это разделение полезно по трём причинам:

- Легче читать код по слоям.
- Проще тестировать каждую часть отдельно.
- Можно жёстко удерживать границу: диалог не подменяет математику, а математика не занимается HTML.

Ниже та же идея в виде простой ASCII-карты:

```text
[Браузер / API client]
          |
          v
[apps/webapp]
FastAPI + thread/session API + legacy fallback
          |
          +------------------------------+
          |                              |
          v                              v
   [apps/chat_web]                  [legacy /legacy]
Next.js + CopilotKit + AG-UI        HTMX/Jinja fallback
          |
          v
[packages/agent_core]
AgentService
DialogGraph + typed semantics
Session state
NL/command parsing
Explanation
          |
          +------------------------------+
          |                              |
          v                              v
[LiteLLM / внешняя модель]      [packages/or_core]
optional help only              ScenarioAssembler
patch suggestion + explanation  ORPipeline
                                4 deterministic solvers
                                          |
                                          v
                                      [ORResult]
```

Если хочется сразу сверять рассказ с кодом, то самые важные входные точки находятся в:

- `apps/webapp/src/webapp/main.py`
- `packages/agent_core/src/agent_core/service.py`
- `packages/agent_core/src/agent_core/dialog_graph.py`
- `packages/or_core/src/or_core/scenario.py`
- `packages/or_core/src/or_core/pipeline.py`

## 3. Не путайте два разных смысла слова "агент"

В этом репозитории слово "агент" используется в двух разных смыслах.

### 3.1 Runtime-агент внутри продукта

Это тот ассистент, с которым разговаривает пользователь приложения.

Он:

- хранит `AgentSession`,
- ведёт диалог,
- помогает собрать входы,
- запускает OR-пайплайн,
- объясняет результат.

Это продуктовая архитектура проекта.

### 3.2 Внешний coding-agent, который работает с репозиторием

Это уже не часть пользовательского приложения, а часть процесса разработки.

Он:

- читает `AGENTS.md`,
- работает с beads-задачами,
- должен соблюдать flush-only workflow,
- запускает безопасные `make bd-*` команды,
- не должен использовать raw `bd sync`.

Это важно, потому что иначе легко перепутать:

- "агент в приложении" — это объект доменной архитектуры;
- "агент-разработчик" — это инженерный инструмент, который вносит изменения в репозиторий.

Для архитектурного понимания продукта основной интерес представляет runtime-агент.
Но для работы с проектом как с репозиторием правила из `AGENTS.md` тоже нужно помнить.

## 4. Что происходит за один ход диалога

Один "ход" — это одно сообщение пользователя и один ответ системы.

Внутри это выглядит так:

```text
User
  |
  | message
  v
/api/chat/threads/{thread_id}/turn
  |
  v
AgentService.handle_slash_turn()
  |
  +--> get/create AgentSession
  +--> ConversationOrchestrator.handle(...)
          |
          +--> add_user_message
          +--> collect_inputs
                  |
                  +--> parse slash или semantics-driven NL
                  +--> reject bare legacy commands in /app path
                  +--> update ScenarioDraft / confirmation state
                  +--> recompute missing_fields / ready_to_run
                  |
                  +--> if no run:
                  |       assistant answers immediately
                  |
                  +--> if explicit run and inputs valid:
                          ScenarioAssembler.build_from_draft()
                          ORPipeline.run()
                          explain_result_for_student()
  |
  +--> save updated session
  v
JSON TurnResult (thread API)
```

Самое важное в этом flow:

- сообщение не идёт напрямую в OR-солверы;
- сначала оно проходит через слой диалога и валидации;
- команды без `/` (`start/json/set/run`) в `/app` не исполняются и считаются legacy-only;
- OR-запуск происходит только по явной команде `/solve` (или эквивалентному solve-intent);
- если входы неполные или есть неподтверждённые patch-и, расчёт блокируется;
- после успешного расчёта в сессию сохраняется `or_result`, а затем строится объяснение.

## 5. Сквозной учебный сценарий: от свободного текста до результата

Ниже упрощённая история, которая хорошо показывает весь цикл.

### Шаг 1. Пользователь начинает сбор входов

Пользователь отправляет:

```text
/new default_or
```

Система создаёт пустой `ScenarioDraft` и подсказывает, что сейчас нужно заполнить stage `production`.

### Шаг 2. Пользователь пишет свободным текстом

Например:

```text
production products ["A","B"], profits [40,30]
```

NL-слой не пишет эти данные сразу в draft.
Он сначала строит `candidate patches`, то есть предполагаемые структурированные изменения:

- `production.products = ["A", "B"]`
- `production.profits = [40, 30]`

И только потом просит подтверждение `да/нет`.

### Шаг 3. Пользователь подтверждает

Если пользователь отвечает:

```text
да
```

тогда подтверждённые patch-и реально применяются к `ScenarioDraft`.

Это важный защитный механизм:

- сначала "я понял вот так",
- потом "подтверди",
- только потом "записываю в состояние".

### Шаг 4. Так повторяется для остальных stage

Пользователь постепенно вводит параметры для:

- `production`,
- `shipment`,
- `assignment`,
- `routing`.

На этом этапе система всё время пересчитывает:

- какие поля ещё отсутствуют,
- какие stage невалидны,
- готов ли draft к запуску,
- какой вопрос нужно задать следующим.

### Шаг 5. Пользователь явно запускает расчёт

Когда все 4 stage готовы, пользователь отправляет:

```text
run
```

Именно здесь происходит переход от "диалогового режима" к "режиму вычисления".

### Шаг 6. `ScenarioDraft` превращается в `ORPipelineInput`

Перед настоящим расчётом система:

- валидирует каждый stage отдельно;
- проверяет согласованность между stage;
- собирает единый `ORPipelineInput`.

Если здесь что-то не сходится, пользователь не получает `500`, а видит понятную ошибку.

### Шаг 7. OR-пайплайн проходит 4 этапа

После успешной сборки запускается цепочка:

1. `Production`
2. `Shipment`
3. `Assignment`
4. `Routing`

Эти этапы связаны друг с другом данными, а не просто стоят рядом по красоте.

### Шаг 8. Строится объяснение результата

После OR-расчёта система пытается объяснить ответ студенту.

Если LLM-провайдер доступен, он может помочь сформулировать объяснение.
Если провайдер недоступен, проект не ломается: используется детерминированный fallback-шаблон.

## 6. Как живёт `AgentSession`

`AgentSession` — это главный объект состояния пользовательского диалога.
Если представить систему как игру с сохранением прогресса, то `AgentSession` и есть этот save file.

Ниже полезно смотреть на поля не как на "просто схему", а как на историю того, что происходит с пользователем.

| Поле | Простыми словами | Когда меняется |
| --- | --- | --- |
| `messages` | История диалога | На каждом user/assistant ходе |
| `scenario_draft` | Черновик независимых входов для 4 stage | Когда пользователь вводит или подтверждает параметры |
| `collection_state` | Где мы находимся в процессе сбора входов | После каждого шага диалога |
| `confirmation_state` | Есть ли patch-и, которые ещё ждут `да/нет` | После NL extraction и после подтверждения/отклонения |
| `missing_fields` | Какие stage пока не готовы | После каждой валидации draft |
| `validation_errors_by_stage` | Почему конкретный stage считается неготовым | После каждой валидации draft |
| `teaching_hints` | Короткие учебные подсказки по важным полям | Когда NL extraction распознал знакомые поля |
| `nl_uncertainties` | Что именно система не поняла в свободном тексте | Когда NL parsing не уверен |
| `pre_run_summary` | Короткая памятка перед запуском | Когда все 4 stage уже готовы |
| `pending_question` | Следующий лучший вопрос к пользователю | Почти после каждого хода |
| `or_result` | Итог 4-этапного OR-расчёта | После успешного `run` |
| `explanation` | Текстовое объяснение результата | После шага explain |
| `warnings` / `errors` | Диагностика и деградационные сообщения | При проблемах провайдера, валидации или OR-пайплайна |
| `model_alias` | Какая модель выбрана для LLM-задач | Когда пользователь выбирает модель |

### Что особенно важно помнить про `AgentSession`

- Это не просто лог чата. Это одновременно и история сообщений, и черновик предметной модели, и место для результатов расчёта.
- Старый `or_result` не считается вечной истиной. Если пользователь меняет входы, кэш результата сбрасывается.
- `pending_question` нужен не для красоты UI, а чтобы система всегда могла показать следующий осмысленный шаг.

### Что такое `collection_state`

`collection_state` — это компактный ответ на вопрос "где мы сейчас в диалоге?".

У него есть два особенно полезных измерения:

- `mode`
  - `wizard` — обычный пошаговый режим;
  - `json` — пользователь прислал готовый JSON для stage;
  - `nl` — система работает через свободный текст и подтверждение patch-ей.
- `phase`
  - `drafting` — входы ещё собираются;
  - `awaiting_confirmation` — ждём `да/нет` для `candidate patches`;
  - `ready_to_run` — всё готово, можно запускать;
  - `running` — OR-пайплайн уже выполняется.

## 7. Что именно вводит пользователь в 4 stage и что эти stage передают дальше

Одна из самых полезных идей для новичка: пользователь вводит не все данные мира.
Он вводит только независимые входы, а часть данных вычисляется и передаётся дальше автоматически.

### `Production`

Пользователь задаёт:

- продукты,
- прибыль,
- матрицу ресурсов,
- лимиты ресурсов,
- верхние границы спроса,
- коэффициенты паллет.

Этот этап отвечает на вопрос:
"Сколько чего выгодно производить?"

Он передаёт дальше:

- `total_pallets`

То есть общий доступный объём для следующего этапа отгрузки.

### `Shipment`

Пользователь задаёт:

- склады,
- доли supply по складам,
- клиентов,
- спрос клиентов,
- матрицу стоимостей,
- матрицу пропускных способностей.

Этот этап отвечает на вопрос:
"Как распределить доступный объём по клиентам с минимальной стоимостью?"

Он передаёт дальше:

- `tasks` для assignment;
- `client_delivery` для routing.

### `Assignment`

Пользователь задаёт:

- ресурсы;
- матрицу стоимости назначения.

Этот этап отвечает на вопрос:
"Какой ресурс должен обслужить какую клиентскую задачу?"

Он передаёт дальше:

- пары `resource -> client/task`;
- ограничения на допустимые транспортные средства для клиентов.

### `Routing`

Пользователь задаёт:

- матрицу расстояний,
- индекс депо,
- узлы клиентов,
- ёмкости транспортных средств,
- при необходимости objective.

Этот этап отвечает на вопрос:
"Как построить маршруты транспорта?"

Но здесь есть важная тонкость:

- пользователь не вводит `routing.client_demands` вручную;
- эти demand-ы выводятся из `ShipmentOutput.client_delivery`.

Это хороший пример того, зачем pipeline вообще нужен: следующий этап получает данные не только от пользователя, но и от предыдущих этапов.

## 8. Что делает LLM, а что он не делает никогда

Этот проект специально построен так, чтобы LLM был помощником, а не судьёй истины.

### LLM делает

- помогает извлечь `candidate patches` из свободного текста, если детерминированного разбора недостаточно;
- помогает сформулировать объяснение уже посчитанного результата;
- может деградировать без остановки всей системы.

### LLM не делает

- не записывает значения напрямую в `ScenarioDraft` без подтверждения;
- не подменяет валидацию `ScenarioAssembler`;
- не подменяет OR-солверы;
- не запускает расчёт сам по себе;
- не отменяет требование явной команды `run`;
- не отменяет блокировку при неподтверждённых patch-ах.

Если упростить до одной фразы:

> LLM здесь помогает общаться с системой, но не принимает математические и структурные решения за неё.

## 9. Что упрощено ради обучения

Этот проект учебный, поэтому в нём сознательно выбраны некоторые упрощения.

- Сессии хранятся в `InMemorySessionStore`, а не в базе данных.
- `base_scenario.json` используется как optional preset, а не как скрытая автоподстановка.
- Объяснение результата имеет deterministic fallback, чтобы проект был полезен даже без внешнего провайдера.
- Документация и docstring-и написаны так, чтобы студент мог читать не только "что", но и "зачем".

Это не "недостатки" проекта. Наоборот, это архитектурные решения, которые уменьшают шум и позволяют лучше увидеть основную механику.

## 10. Мини-глоссарий

- `stage` — один из четырёх независимых этапов сбора входов: `production`, `shipment`, `assignment`, `routing`.
- `ScenarioDraft` — черновик независимых входных данных, который пользователь собирает в чате.
- `candidate patch` — предполагаемое изменение draft, извлечённое из свободного текста и ещё не подтверждённое пользователем.
- `confirmation` — шаг `да/нет`, после которого `candidate patch` либо применяется, либо отбрасывается.
- `ready_to_run` — состояние, когда все входы валидны и можно выполнять `run`.
- `pending_question` — следующий лучший вопрос, который система хочет задать пользователю.
- `ORPipelineInput` — итоговый строго валидированный вход для OR-конвейера.
- `ORResult` — результат всех четырёх этапов плюс `final_report` и `execution_trace`.
- `execution_trace` — список имён этапов, реально выполненных OR-пайплайном.
- `fallback` — запасной путь, который сохраняет полезность системы при недоступности провайдера или при низкой уверенности.
- `model_alias` — человеко-устойчивое имя выбранной модели, например `openai_default` или `local_default`.
- `preset` — заранее подготовленный сценарий, который можно загрузить командой `load preset demo`.
