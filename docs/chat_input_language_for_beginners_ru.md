# Язык ввода чата для новичков

Этот документ объясняет, каким языком нужно пользоваться при работе с учебным чатом.
Здесь слово "язык" не означает полноценный язык программирования, но и не означает
"совсем свободный разговор". На практике это полу-DSL поверх обычного чата:
часть сообщений должна быть очень точной, а часть можно писать свободнее, но с
ожидаемой структурой и последующим подтверждением.

Если вам нужен общий tutorial по работе с чатом, сначала посмотрите
[chat_usage_for_beginners_ru.md](chat_usage_for_beginners_ru.md).
Если нужен короткий контракт именно NL-режима, смотрите
[natural_language_assistant_ru.md](natural_language_assistant_ru.md).

## TL;DR

- Самый безопасный способ ввода: `json <stage> {...}`.
- Самый удобный способ точечной правки: `set <stage>.<field> <value>`.
- Самый удобный способ вставить большой JSON без префикса: `edit <stage>`, потом `{...}`.
- Самый свободный способ: natural-language реплика со stage и полями, но её всегда надо подтвердить через `да` или `нет`.
- `json <stage> {...}` заменяет stage целиком.
- `set` и подтверждённые NL-patch'и меняют только отдельные поля.
- `run` блокируется, если stage не заполнены или если есть неподтверждённые NL-параметры.
- `routing.client_demands` вручную не вводится: это derived-поле, оно берётся из этапа `shipment`.

## 1. Что это за язык на самом деле

У чата есть четыре режима ввода, расположенные по степени строгости:

1. Точные команды управления:
   `start`, `show input`, `next`, `run`, `reset`, `load preset demo`.
2. Строгий stage-ввод:
   `json <stage> {...}`.
3. Точечные правки:
   `set <stage>.<field_path> <value>`.
4. Свободный, но не совсем произвольный natural-language:
   сообщения в духе `production profits [40,30], products ["A","B"]`.

Главная идея простая:

- если вам нужна предсказуемость, пишите как команду;
- если вам нужна скорость, можно писать почти человеческим языком;
- но чем свободнее формулировка, тем больше шанс, что чат попросит уточнение или подтверждение.

## 2. Точный контракт: какие формы реально понимает чат

Ниже перечислены формы, которые подтверждены кодом parser-а и графа.

### 2.1 Команды управления

- `start`
- `старт`
- `reset`
- `сброс`
- `help`
- `помощь`
- `show input`
- `show`
- `показать ввод`
- `показать`
- `next`
- `далее`
- `run`
- `запуск`
- `load preset demo`
- `preset demo`
- `load demo`
- `загрузить демо`

### 2.2 Команды выбора stage и ввода данных

- `edit <stage>`
- `json <stage> <json-object>`
- `set <stage>.<field_path> <value>`
- чистый JSON-объект `{...}` без команды, но только если у сессии уже известен `current_stage`

Практически это означает:

- `edit <stage>` сам по себе ничего не записывает, а только выбирает stage для следующего шага;
- raw JSON `{...}` безопаснее всего использовать сразу после `edit <stage>`;
- после `start` и `next` у чата тоже есть `current_stage`, но новичку проще опираться именно на явный `edit <stage>`.

### 2.3 Подтверждение и отклонение NL-параметров

Подтверждение:

- `да`
- `подтверждаю`
- `подтвердить`
- `ок`
- `согласен`

Отклонение:

- `нет`
- `отмена`
- `не подтверждаю`
- `отклонить`
- `не так`

### 2.4 NL-маркеры, которые чат понимает отдельно от точных команд

Run-intent:

- `run`
- `запусти`
- `запуск`
- `посчитай`
- `рассчитай`

Help-intent:

- `help`
- `помощь`
- `что дальше`
- `как вводить`

Важно: слова вроде `запусти` и `как вводить` относятся к NL-слою.
Если в сообщении одновременно есть и такие маркеры, и структурированные поля,
сначала произойдёт извлечение параметров, а не запуск действия.

## 3. Насколько строго надо придерживаться этого языка

Проще всего думать о вводе как о четырёх уровнях строгости.

### Уровень 1. Самый строгий и самый безопасный

Используйте:

```text
json <stage> {...}
```

Пример:

```text
json production {"products":["A","B"],"profits":[40,30],"resource_matrix":[[2,1],[1,1.5]],"resource_limits":[240,180],"demand_upper_bounds":[70,80],"pallet_factors":[1.0,0.8]}
```

Этот режим лучше всего подходит для первого полного ввода stage.

### Уровень 2. Точечные правки

Используйте:

```text
set <stage>.<field_path> <value>
```

Пример:

```text
set production.profits [41,31]
```

Этот режим лучше всего подходит, когда stage уже почти готов и нужно поменять
одно конкретное поле.

### Уровень 3. Удобный stage-by-stage ввод

Используйте:

```text
edit <stage>
{...}
```

Пример:

```text
edit shipment
{"warehouses":["W1","W2"],"warehouse_supply_ratio":[0.55,0.45],"clients":["C1","C2","C3"],"client_demand":[42,38,40],"cost_matrix":[[4,6,8],[5,4,3]],"capacity_matrix":[[50,45,40],[40,45,50]]}
```

Это удобно, когда вы заранее подготовили объект для одного stage, но не хотите
печатать префикс `json shipment ...`.

### Уровень 4. Самый вольный, но подтверждаемый

Используйте natural-language сообщение:

```text
production profits [40,30], products ["A","B"]
```

или:

```text
для shipment cost_matrix [[4,6,8],[5,4,3]]
```

Этот режим удобен для быстрых проб, но у него всегда есть цена:
чат покажет `candidate patches` и будет ждать `да` или `нет`.

## 4. Можно ли вводить данные по кусочкам

Да, можно. Это нормальный режим работы системы.

Но тут есть важные правила.

### 4.1 Что делает `json <stage> {...}`

`json <stage> {...}` заменяет весь stage-объект целиком.

Это значит:

- если вы забыли поле, оно не "доживёт" из старой версии stage;
- после нового `json production {...}` stage `production` состоит ровно из тех полей, которые лежат в этом JSON;
- поэтому `json` лучше использовать для полного описания stage, а не для маленькой правки.
- raw JSON shortcut `{...}` для `current_stage` ведёт себя так же: он тоже заменяет весь текущий stage-объект.

### 4.2 Что делает `set`

`set` обновляет только одно поле по пути `stage.field_path`.

Это значит:

- старые соседние поля stage сохраняются;
- повторный `set` просто перезапишет прошлое значение;
- `set` удобно использовать после полного `json`, когда нужно скорректировать 1-2 поля.

### 4.3 Что делают подтверждённые NL-patch'и

Подтверждённые natural-language patch'и ведут себя как точечные изменения:

- они merge/overwrite только перечисленные поля;
- остальные поля stage не трогаются;
- пока вы не ответили `да`, они не применяются.

### 4.4 Что происходит с результатом после любого изменения

После изменения входов старый `or_result` инвалидируется.

Поэтому нормальная последовательность такая:

1. ввести или поправить данные;
2. убедиться, что всё готово;
3. только потом снова отправить `run`.

### 4.5 Когда `run` не сработает

`run` блокируется, если:

- не заполнены все обязательные поля stage;
- есть ошибки валидации;
- висят неподтверждённые NL-patch'и.

## 5. Какой workflow лучше использовать студенту

Самый практичный базовый workflow такой:

1. Отправить `start`.
2. Идти по stage в порядке:
   `production -> shipment -> assignment -> routing`.
3. Для первого полного ввода stage использовать `json <stage> {...}`.
4. Для маленьких исправлений использовать `set`.
5. Для быстрых гипотез и маленьких проб использовать NL-режим, но сразу проверять и подтверждать `candidate patches`.
6. Периодически использовать `show input`.
7. Только после полной готовности отправлять `run`.

Если хочется максимально безопасный режим без догадок чата, используйте только:

- `start`
- `json <stage> {...}`
- `set <stage>.<field> <value>`
- `show input`
- `run`

## 6. Как именно парсятся значения в `set`

Команда `set` сначала пытается распарсить значение как JSON, а потом использует
более простые fallback-правила.

### 6.1 Поддерживаемые типы

- JSON-массивы:
  `set shipment.client_demand [42,38,40]`
- JSON-объекты:
  `set routing.meta {"note":"demo"}`
- целые числа:
  `set routing.depot_index 0`
- числа с плавающей точкой:
  `set production.pallet_factors [1.0,0.8]`
- булевы значения:
  `set routing.some_flag true`
- строки:
  `set production.comment тестовый_запуск`

### 6.2 Важное следствие

Если значение не получилось распарсить как JSON, `true/false`, `int` или `float`,
оно останется строкой.

Поэтому:

- массивы и объекты лучше писать в JSON-виде;
- числа лучше писать без лишних слов;
- строки лучше считать fallback-вариантом, а не основным способом задания модели.

## 7. Stage-by-stage guide по всей цепочке

Ниже идут одинаково устроенные подсекции для каждого stage:

- что это за этап;
- какие поля обязательны;
- что можно вводить частями;
- какой способ лучше использовать;
- copy-paste примеры.

### 7.1 `production`

Что делает этот stage:
задаёт LP-входы для этапа производства.

Обязательные поля:

- `products`
- `profits`
- `resource_matrix`
- `resource_limits`
- `demand_upper_bounds`
- `pallet_factors`

Что удобно вводить частями:

- `profits`
- `resource_limits`
- `demand_upper_bounds`
- `pallet_factors`

Рекомендуемый первый ввод:
полный `json production {...}`.

Полный JSON-пример:

```text
json production {"products":["A","B"],"profits":[40,30],"resource_matrix":[[2,1],[1,1.5]],"resource_limits":[240,180],"demand_upper_bounds":[70,80],"pallet_factors":[1.0,0.8]}
```

Примеры `set`:

```text
set production.profits [41,31]
set production.resource_limits [250,190]
set production.demand_upper_bounds [72,78]
```

Пример natural-language:

```text
production profits [41,31], pallet_factors [1.0,0.8]
```

### 7.2 `shipment`

Что делает этот stage:
задаёт шаблон транспортировки от складов к клиентам.

Обязательные поля:

- `warehouses`
- `warehouse_supply_ratio`
- `clients`
- `client_demand`
- `cost_matrix`
- `capacity_matrix`

Что удобно вводить частями:

- `warehouse_supply_ratio`
- `client_demand`
- `cost_matrix`
- `capacity_matrix`

Рекомендуемый первый ввод:
полный `json shipment {...}`.

Полный JSON-пример:

```text
json shipment {"warehouses":["W1","W2"],"warehouse_supply_ratio":[0.55,0.45],"clients":["C1","C2","C3"],"client_demand":[42,38,40],"cost_matrix":[[4,6,8],[5,4,3]],"capacity_matrix":[[50,45,40],[40,45,50]]}
```

Примеры `set`:

```text
set shipment.client_demand [40,39,41]
set shipment.cost_matrix [[4,6,8],[5,5,3]]
set shipment.capacity_matrix [[52,45,40],[38,45,50]]
```

Пример natural-language:

```text
shipment client_demand [42,38,40], cost_matrix [[4,6,8],[5,4,3]]
```

### 7.3 `assignment`

Что делает этот stage:
задаёт соответствие ресурсов и клиентов для этапа назначения.

Обязательные поля:

- `resources`
- `cost_matrix`

Что удобно вводить частями:

- практически любой из двух параметров, но чаще правят `cost_matrix`

Рекомендуемый первый ввод:
полный `json assignment {...}`.

Полный JSON-пример:

```text
json assignment {"resources":["truck_1","truck_2","truck_3"],"cost_matrix":[[8,6,7],[5,8,6],[7,5,9]]}
```

Примеры `set`:

```text
set assignment.resources ["truck_1","truck_2","truck_3"]
set assignment.cost_matrix [[7,6,7],[5,8,6],[7,5,8]]
set assignment.cost_matrix [[8,6,7],[5,7,6],[7,5,9]]
```

Пример natural-language:

```text
assignment resources ["truck_1","truck_2","truck_3"], cost_matrix [[8,6,7],[5,8,6],[7,5,9]]
```

### 7.4 `routing`

Что делает этот stage:
задаёт независимый routing-шаблон до того, как система подставит фактические объёмы из shipment.

Обязательные поля:

- `distance_matrix`
- `depot_index`
- `client_nodes`
- `vehicle_capacities`

Необязательное поле:

- `objective`
  По умолчанию: `total_distance`

Что удобно вводить частями:

- `depot_index`
- `client_nodes`
- `vehicle_capacities`
- `objective`

Рекомендуемый первый ввод:
полный `json routing {...}`.

Полный JSON-пример:

```text
json routing {"distance_matrix":[[0,10,12,8],[10,0,6,7],[12,6,0,9],[8,7,9,0]],"depot_index":0,"client_nodes":[1,2,3],"vehicle_capacities":[55,45,45],"objective":"total_distance"}
```

Примеры `set`:

```text
set routing.depot_index 0
set routing.client_nodes [1,2,3]
set routing.vehicle_capacities [55,45,45]
```

Пример natural-language:

```text
routing depot_index 0, client_nodes [1,2,3], vehicle_capacities [55,45,45]
```

Важное замечание:

- `routing.client_demands` вручную не вводится;
- это не часть пользовательского DSL для чата;
- система получает это значение из этапа `shipment`.

## 8. Что лучше писать свободным текстом, а что не стоит

Хорошо работает:

- `production profits [40,30], products ["A","B"]`
- `shipment client_demand [42,38,40]`
- `routing depot_index 0, client_nodes [1,2,3]`
- `для shipment cost_matrix [[4,6,8],[5,4,3]]`

Плохо работает или часто требует уточнение:

- "сделай всё как в прошлый раз, но немного дороже"
- "введи данные для доставки"
- "для production и shipment задай cost_matrix [[1,2],[2,1]]"
- "запусти и заодно поставь profits [40,30]"

Практическое правило:

- если хотите стабильности, пишите stage и field явно;
- если хотите написать сразу много входов, лучше используйте `json`;
- если чат начал задавать уточняющие вопросы, это не ошибка системы, а признак того, что формулировка была слишком свободной.

## 9. Командные и NL-alias'ы, которые лучше всего помнить

### 9.1 Самые безопасные stage-имена

Лучше всего писать канонические формы:

- `production`
- `shipment`
- `assignment`
- `routing`

### 9.2 Командные stage-alias'ы

Командный parser понимает:

- `production`, `prod`, `производство`
- `shipment`, `ship`, `отгрузка`
- `assignment`, `assign`, `назначение`
- `routing`, `route`, `маршрутизация`

### 9.3 NL-stage-alias'ы

NL parser дополнительно узнаёт:

- `выпуск` для `production`
- `доставка` для `shipment`
- `маршруты` для `routing`

### 9.4 Поля, которые NL-режим узнаёт лучше всего

`production`:

- `products`, `продукты`
- `profits`, `прибыль`
- `resource_matrix`, `матрица ресурсов`
- `resource_limits`, `лимиты ресурсов`
- `demand_upper_bounds`, `спрос`
- `pallet_factors`, `коэффициенты паллет`

`shipment`:

- `warehouses`, `склады`
- `warehouse_supply_ratio`, `доли складов`
- `clients`, `клиенты`
- `client_demand`, `спрос клиентов`
- `cost_matrix`, `матрица стоимости`
- `capacity_matrix`, `матрица пропускной способности`, `capacity`

`assignment`:

- `resources`, `ресурсы`, `машины`
- `cost_matrix`, `матрица назначения`

`routing`:

- `distance_matrix`, `матрица расстояний`
- `depot_index`, `депо`
- `client_nodes`, `узлы клиентов`
- `vehicle_capacities`, `емкости`, `ёмкости`
- `objective`, `цель`

## 10. Мини-cheat sheet

Если нужен самый простой и надёжный набор правил, используйте такой шаблон:

1. `start`
2. `json production {...}`
3. `json shipment {...}`
4. `json assignment {...}`
5. `json routing {...}`
6. при необходимости `set ...`
7. `show input`
8. `run`

Если хочется свободы:

1. Пишите stage и поле явно.
2. Смотрите, какие `candidate patches` извлёк чат.
3. Подтверждайте `да` только то, что действительно хотите применить.
4. Если чат сомневается, возвращайтесь к `json` и `set`.
